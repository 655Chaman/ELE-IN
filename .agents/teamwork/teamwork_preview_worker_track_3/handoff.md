1. **`core/frontend/lib/apiClient.ts` (Lines 18–32)**:
   In `fetchWithAuth`:
   ```ts

   ```
   If `path` was passed as relative `/api/approvals` without base URL normalization, environments without Vite reverse-proxy or where `VITE_API_URL` was explicitly configured would fail to resolve backend endpoints or create double/missing slashes.

2. **`core/backend/workers/job_processor.py` (Lines 84–90)**:
   In `process_single_job`:
   ```python
   account_id = payload.get('account_id')
   ws_id = payload.get('workspace_id', workspace_id)
   
   acc_res = sync_supabase.table("accounts").select("session_cookies_encrypted, proxies(protocol, host, port, username)").eq("id", account_id).execute()
   if not acc_res.data:
       raise ValueError(f"Account {account_id} not found.")
   ```
   `job_processor.py` strictly extracted `account_id` from `payload.get('account_id')`. Because previous versions of `approvals.py` only passed `account_id` as `asset_id` into `enqueue_job(supabase, 'inbox_action', workspace_id, asset_id, payload)` and omitted `'account_id'` from `payload`, `account_id` evaluated to `None`, triggering `ValueError: Account None not found.` and failing LinkedIn message dispatch entirely.

3. **`core/backend/api/routers/approvals.py` (`approve_reply`, Lines 65–116)**:
   - Only queried `approval_queue`. Items generated by campaign AI replies in `ai_reply_approvals` (created in `elein_executor.py` lines 1173–1185) threw 404.
   - Enqueued `inbox_action` with `payload = {'action': 'send_message_to_existing_thread', 'payload_data': {'sender_name': item['sender_name'], 'message': final_message}}`, omitting `'account_id'` and `'workspace_id'`.
   - Never updated `campaign_execution_states` (`status: "pending"`), leaving leads frozen.

4. **`core/backend/api/routers/approvals.py` (`reject_reply`, Lines 118–139)**:
   - Only queried `approval_queue`, updating `status: "skipped"`.
   - Completely omitted updating `campaign_execution_states` to `status: "exited"`, `error_reason: "ai_reply_rejected"`. As a result, any lead waiting for approval remained permanently stuck in `awaiting_approval` until the 48-hour expiration reaper.

5. **`core/backend/api/routers/approvals.py` (`list_approvals` and `get_approval`, Lines 18–64)**:
   - Both endpoints only queried `approval_queue`. Campaigns recording review items into `ai_reply_approvals` were invisible to the user in the UI at `inbox/frontend/EleInApprovals.tsx`.

## 2. Logic Chain

1. *From Observation 1*: `apiClient.ts` must normalize incoming URLs by inspecting `import.meta.env.VITE_API_URL` (if present) and ensuring absolute URLs (`http://`, `https://`) remain untouched while relative paths receive the normalized API base with clean leading/trailing slash handling.
2. *From Observation 2*: When `job_processor.py` processes `inbox_action` and `inbox_sync`, adding a fallback `account_id = payload.get('account_id') or job.get('asset_id')` ensures that even if an enqueued job's payload omits `account_id`, the worker gracefully resolves it from the job record's `asset_id`. Adding payload string/dict guards prevents `AttributeError` on malformed inputs.
3. *From Observation 3*: In `approvals.py`:
   - `approve_reply` must query `approval_queue` first, then fall back to `ai_reply_approvals`.
   - For `ai_reply_approvals` items, `account_id` is resolved from `campaign_enrollments` or `campaign_accounts` (or active workspace accounts), `sender_name` is resolved from `leads`, and `final_message` is taken from `payload.edited_message` or `generated_reply`.
   - The job payload passed to `enqueue_job` must include `'account_id': account_id` and `'workspace_id': workspace_id` in addition to `'action'` and `'payload_data'`.
   - The approval record is marked `status: "approved"`.
   - The associated `campaign_execution_states` record is updated to `status: "pending"`, `next_run_at: now` so the campaign engine immediately resumes processing the lead.
4. *From Observation 4*: In `reject_reply`:
   - Queries `approval_queue` (updating to `status: "skipped"`) or `ai_reply_approvals` (updating to `status: "rejected"`).
   - Unblocks `campaign_execution_states` by updating it to `status: "exited"`, `error_reason: "ai_reply_rejected"`.
5. *From Observation 5*: `list_approvals` and `get_approval` now query both `approval_queue` and `ai_reply_approvals`, formatting the response so that the frontend (`EleInApprovals.tsx`) displays all pending reviews seamlessly regardless of whether they originated from inbox auto-replies or campaign workflows.

## 3. Caveats

1. **LinkedIn Worker Execution**: In live production, actual message transmission over LinkedIn requires decrypted cookies and active network access by `LinkedInWorker`. The changes made here guarantee that the payload and jobs are correctly structured and enqueued without worker parameter exceptions.
2. **Historical Orphaned Records**: Any leads that were previously frozen in `awaiting_approval` before this fix will be unblocked on subsequent approval/rejection actions or by the 48-hour reaper in `elein_orchestrator.py`.
